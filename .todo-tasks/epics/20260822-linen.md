## What Linen is

Linen is a new Luminous app (platform: doc01.04). Its goal: look at any piece of
a software project and say "what happens when this runs." The product idea is
`.rhidoc/01-product/09-linen/01-idea.md` (doc01.09.01); the controlled
vocabulary is `.rhidoc/01-product/09-linen/02-glossary.md` (doc01.09.02).
**Read both before implementing anything. Use the glossary terms exactly —
Trace, Trace Node, Glyph, Edge, Entry, Filter, Switch, Transformation, Type,
Pass, Return, Release Control, Module, Deployment, Contract, Manifest,
Document. Never coin a synonym; a concept the glossary does not name gets an
Unnamed entry surfaced to the user, never a name invented in passing.**

Linen differs from Atlas in rendering: Trace Nodes are drawn as small Glyphs
(symbols), not content boxes; a Trace Node's detail appears in an annotation
panel when selected ("click one → what happens here?"). Containers are Modules
(ownership boundaries), nestable (Deployment above Module).

## Locked design decisions

1. **The return rule.** No bidirectional Edge shows control returning. When a
   Pass hands control to another Module, the caller's Trace resumes holding
   data in the format of the Contract connected to the Module passed to. The
   return side is derived from that connection, never drawn or stored.
2. **Authored facts are stored; derivable facts are computed.** A Document
   records only what a human declared. Conclusions — the format a Trace
   resumes with after a Pass, a Module border's Manifest, trace order beyond
   the edge list — are computed at projection/check time and never persisted.
   A rule change must never require a Document migration.
3. **One descriptor table.** Each Trace Node type is one entry in a single
   core table (name, gloss, glyph id, structural rules as data). Checks,
   rendering, MCP schemas, and generated references derive from the table.
   Renames are a table edit plus a version-keyed migration in `migrate.ts` —
   names are expected to change, so changing them must be mechanical. The
   existing pattern to copy: `packages/core/src/render/primitive-descriptors.ts`
   with `just gen-skill-reference` / `just check-skill-reference`.
4. **Contract is undifferentiated.** No "output Contract" subtype, no
   decoration of that fact. Just Contract (unfolding principle: differentiate
   only when forces demand).
5. **Human owns vocabulary and composition; AI implements from specs.** From
   the whiteboard: "AI cannot decide: composition, controlled vocabulary."
   During implementation, a needed-but-unnamed concept is a stop-and-surface,
   never a silent coinage (see doc00.05 "Naming" and the fifa-bracketing
   retrospective doc01.05.02).

## Document schema (authored facts only)

`*.linen.json`. TypeScript owns the shape (`packages/core/src/linen/types.ts`):

- `LinenDocument { v: 1, modules, contracts, nodes, edges }`
- `LinenModule { id, name, parent? }` — `parent` nests a Module inside another
  (a Deployment is a Module containing Modules; no separate type yet).
- `LinenContract { id, name, owner?, text? }` — `owner` is a Module id;
  `text` is the declared data shape in the described system's notation.
- `LinenTraceNode { id, kind, module, annotation?, x?, y? }` — `kind` is a
  Trace Node type from the descriptor table; `module` is the containing
  Module id; `annotation` is the selected-node prose. A Pass node adds
  `to: moduleId` (the Module passed to). A Type node adds `contract?: contractId`
  when its format is a named Contract rather than free text.
- `LinenEdge { from, to }` — one Edge term, two uses distinguished by target:
  trace-node → trace-node carries control and Trace order; node-or-module →
  contract is an "Edge to a Contract". `check.ts` validates which endpoint
  combinations are legal; no stored discriminant.

Ids are author-supplied and meaningful (Atlas convention). Trace order is
derived by walking control edges from an Entry — never stored as sequence
numbers (decision 2).

  42, 93–98), `packages/server/src/store.ts` (suffix consts ~15–17), raw-write

  connection-drag wiring are reusable. Linen's layout can start as a dumb
  per-Module vertical sequence — sequenced control edges make this trivial.

## First model target

nyc-subwhere (`../nyc-subwhere`), a live 3D NYC subway map: Cloudflare Worker
(`packages/worker/src/index.ts` — fetch handler + `FeedPoller`/`BikePoller`
Durable Objects), browser client (`packages/web/src/main.ts`), shared
type-only contract package (`packages/contract/src/index.ts`). The chosen
Trace, "a train moving on screen":

1. `FeedPoller.alarm()` (worker/src/index.ts:135) loads `TripMemory`.
2. `pollSnapshot` (worker/src/poll.ts:28): `Promise.allSettled` over 8 MTA
   GTFS-realtime feeds; guard: zero successes → keep last good KV frame.
   protobuf `FeedMessage.decode`.
3. `buildSnapshot` (worker/src/reshape.ts:75): guards (needs `tripUpdate.trip`,
   `isAssigned`, usable stop times); branch on motion (STOPPED_AT /
   dead-reckon / stalled >45s overrun).
4. Alarm writes `RenderSnapshot` JSON to KV `trips:snapshot`; `finally`
   re-arms at +30s.
5. Browser `poll()` fetches `/api/trips`; worker serves the KV blob verbatim.
6. `estimator.ingest` (web/src/trains.ts:339): forward-only reconciliation
   (`fromDist = clamp(...)` so revised ETAs bend pace, never snap back).
7. `frame()` per rAF: poses interpolated, `networkLayer.setTrains(poses)`.

This Trace crosses runtimes without a call (KV write → later browser read) —
deliberately the hostile case for the vocabulary. If it cannot be drawn
honestly, surface the gap to the user; do not invent a node type.
